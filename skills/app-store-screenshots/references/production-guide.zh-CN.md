# App Store 上架图片制作说明

这份文档可独立阅读，也可直接交给其他 AI。它总结了一套从产品研究、演示截图到现代视觉设计、多语言导出和 App Store Connect 验证的工作方式。适用于更换产品和电脑；设备、尺寸、页数与色彩均按当前产品决定。

目录：1. 使用方式 · 2. 产品与素材 · 3. 页面策划 · 4. 浅色科技感 · 5. 合成与实现 · 6. 多语言 · 7. 导出与验收 · 8. 上传与异常 · 9. 交付。

## 1. 在其他产品或电脑上使用

克隆 AgentAssets 后，直接把本文件交给 AI 即可，不要求特定模型、浏览器或操作系统。提供产品介绍、当前版本功能、真实截图和目标语言。建议把同级资源中的 `../assets/brief-template.yaml` 复制到产品工作区填写；其中的字段是简报，不会自动驱动某个渲染器。

可直接使用以下请求：

> 阅读这份制作说明，为我的产品制作 App Store 上架图片。产品网站：……；当前版本新增：……；截图目录：……。先阅读网站和实际截图，把卖点与素材对应起来。保持 App 的真实界面，采用与主题协调的现代视觉；如果沿用本说明的浅色科技感，请让蓝青紫渐变、柔光轨道和稀疏粒子在导出图中实际可见。允许按语义使用局部放大、蒙版、双画面和宽屏构图。先做简体中文并完成视觉定稿，再做英文和繁体中文。保留可编辑源，交付 PNG、整组预览和尺寸清单。上传仅在我要求时执行。

作为 skill 使用时，资源根目录是 `skills/app-store-screenshots`，入口是 `SKILL.md`。不要只复制入口，丢掉相对引用的说明、模板和脚本。

若消费项目已使用 ctxpm，在资源已提交并可从远端获取后，可在该项目运行：

```sh
ctxpm add https://github.com/BearD01001/AgentAssets.git \
  --type skill --name app-store-screenshots \
  --source-path skills/app-store-screenshots --ref main --entry SKILL.md
ctxpm validate
```

以该电脑实际安装的 CLI 和项目规则为准；项目维护的依赖应由资源管理器安装到 `.ctxpm/dependencies/`，再生成相应代理的发现路径。仅需文档时无需安装或初始化资源管理器。迁移时不要带上旧电脑绝对路径、账号会话或密钥。

## 2. 先了解产品，再准备截图

### 产品资料

真正阅读用户给出的产品网站、相关语言页面、当前版本说明与现有上架图。记录核心用户、使用场景、差异和可核实的能力。旧封面用于识别遗漏和改进点，不能自动视为视觉方向。

把信息分成已发布能力、本版新增能力、待确认能力。官网可能落后于当前版本，应结合用户明确补充和实际界面。例如产品从“卡片收纳”扩展到“卡片与文档”，新的主叙事必须覆盖文档空间，而不是继续只讲卡片。

建一张工作表：

| 用户收益 | 事实依据 | 对应截图 | 建议表达 | 缺口 |
| --- | --- | --- | --- | --- |
| 文件集中管理 | 当前版本功能 + 实际文档库 | 文档首页、预览页 | 库与内容叠层 | 无 |
| 导出前标注用途 | 产品说明 + 水印界面 | 导出编辑与结果 | 操作与结果并置 | 若缺文档截图则标明 |
| 宽屏更易浏览 | 实际宽屏布局 | 宽屏预览与信息 | 宽屏主画面 | 核实真实设备名称 |

“本地保存”不等于“端到端加密”，“设备解锁”不等于自行实现了生物识别，“水印”不等于能阻止传播。文案只表达有依据的能力。

### 演示数据和捕获

用户提供的已选截图优先级高。逐张查看实际内容，不仅看名字；名为 Home 的图片可能实际是详情页。保留原图，只在副本或合成层上处理。

需要模拟器时，先检查本机可用的设备、系统和实际 App 构建。只在获授权的演示环境造数据，不把测试状态写入用户生产数据。若项目有专门的演示入口、购买测试开关或构建规则，遵循这些规则并记录临时变更的恢复方式。

自然的演示数据比整齐复制更可信：

- 分类数量不必相同，例如有的 2 项、有的 5 项、有的 1 项；这只是示意，不是新固定模板。
- 标题长短、颜色、封面、文档页数、日期和文件类型有自然差异。
- 使用明确的虚构身份、样本合同和演示卡片，避免真实身份信息、有效卡号或个人文件。
- 有足够内容展示结构，但不靠无意义的大量条目填满屏幕。

保持同一组截图的主题、文字大小、导航状态尽量一致。检查正式版名称、演示数据、状态栏、空状态、选中状态与弹窗是否符合叙事。不同预览状态用于蒙版时，列表位置、滚动位置和内容必须一致。

## 3. 按功能语义策划一组图片

每页讲一个主要收益。先安排开场价值、核心能力、差异化能力，再安排适配和补充内容。5–6 页是一次项目的选择，不是普遍要求。

| 页面语义 | 适合构图 | 要点 |
| --- | --- | --- |
| 首页 / 分类收纳 | 主界面 + 详情局部浮层 | 从整体到具体内容 |
| 文档库 | 文档列表 + 实际页面放大 | 让用户看到管理对象 |
| 显示 / 隐藏 | 同位置截图的斜向或纵向蒙版 | 对齐后直观解释状态切换 |
| 导出 / 水印 | 编辑与结果双画面 | 文案与可见结果一致 |
| 解锁 / 私密空间 | 解锁页居中，两侧内容渐隐 | 表现入口与受保护内容的关系 |
| 新设备 / 宽屏适配 | 真实宽屏主画面 + 小幅纵向参照 | 展示布局变化，不只写支持某设备 |

不要强迫每页都摆一台同角度手机。相关性强的素材可组合；无关界面不要为了热闹拼在一起。局部放大要能看出它来自哪张主截图。裁切不得掩盖限制、拼接不存在的流程或伪造按钮。

标题表达用户收益，副标题补充具体能力，短标签只做辅助。首屏标题在商店缩略图下也应清晰。先完成最能代表风格的 1–2 页（如首页、蒙版页），再扩展整组，避免在错误方向上铺满全部语言。

## 4. 可复用的浅色科技感配方

这是针对浅色 App 界面得到认可的方向。其他产品可更换品牌色与主题；用户已有批准样式时以其为准。

### 色彩和层次

按从后到前的顺序组织：

1. 接近白色的淡蓝渐变基底，避免大面积深背景与亮截图割裂。
2. 大面积青色和紫色径向柔光，向透明过渡，营造空间。
3. 2–3 条低对比椭圆轨道与贝塞尔光带；线芯可辨认，外围柔化。
4. 边缘留白处的稀疏小粒子，避开正文和 UI 内容。
5. 有少量彩色柔影的真实截图、白色细边和必要的局部叠层。
6. 深蓝正文、青紫重点标题，保持阅读对比。

一组可用起点，数值均按约 1242 × 2688 画布理解，换尺寸后同比调整：

| 元素 | 参数起点 |
| --- | --- |
| 基底 | `#FAFCFF → #E3F0FF → #F5F5FF`，斜向渐变 |
| 主文字 | `#131F36` |
| 次文字 | `#52647D` |
| 青色 | `#05A8D4` |
| 紫色 | `#6E57E8` |
| 柔光 | 青色峰值透明度约 0.26、紫色约 0.19；半径约 900–1000 px |
| 轨道 | 1.6 px 左右，透明度约 0.09–0.21 |
| 光带 | 约 17–30 px 柔化底带 + 1.7 px 线芯；线芯透明度约 0.28–0.43 |
| 粒子 | 半径约 1.5–3 px，仅边缘及少量空白处可见；固定随机种子 |
| 截图阴影 | 彩色柔影半径约 48–65 px，透明度约 0.18–0.23 |
| 边缘 | 白色细描边，避免粗黑手机外壳抢占内容 |

在网页中可从这样的背景开始：

```css
.poster {
  position: relative;
  overflow: hidden;
  background:
    radial-gradient(ellipse at 92% 38%, rgb(5 168 212 / 26%), transparent 65%),
    radial-gradient(ellipse at 0% 74%, rgb(110 87 232 / 19%), transparent 60%),
    linear-gradient(166deg, #fafcff, #e3f0ff 58%, #f5f5ff);
  color: #131f36;
}
```

CSS 只提供基底，轨道、粒子、截图和文字还需单独绘制。不要写了特效代码就宣称有科技感：必须查看最终 PNG，确认效果没有被不透明背景盖住、被裁切、因为合成顺序消失，或缩小后弱到看不见。增强光带线芯和局部色差通常比整体压暗更合适。

### 字体与比例

以现代无衬线为主，中文可用苹方或具有许可的思源字体，英文可用系统无衬线。换电脑后检查字体是否存在，避免回退导致断行与风格变化。

在 1242 × 2688 示例画布中，左右文字边距约 74–80 px；品牌 32 px、分类 28 px、两行主标题约 98 px、副文案 32 px，截图从顶部约 770–850 px 开始，底部保留短说明。它们是构图参考，不是所有语言的固定坐标。

避免千禧年代感的重浮雕、镜面反射、大块高饱和光板、厚描边和装饰堆积。科技感来自精确层次、光感和清楚的界面细节，不能以牺牲可读性为代价。

## 5. 合成实现

### 技术选择

| 方式 | 适用情况 | 注意点 |
| --- | --- | --- |
| HTML / CSS / SVG | 跨平台编辑、复杂布局和实时预览 | 明确画布尺寸、字体加载、资源路径；导出单张画布，不截浏览器外壳 |
| Canvas | 程序化粒子、蒙版、批量生成 | 按目标像素绘制；文字测量、图片解码完成后再导出 |
| Swift / AppKit / CoreGraphics | macOS 上精确绘图与本地脚本批量输出 | 顶部/底部坐标换算、图形状态隔离、sRGB、无 alpha |
| 设计工具 | 人工精调和团队协作 | 保留可编辑源和可重复导出方式 |

工具可以变化，设计不应依赖某台电脑的绝对路径。把源图路径、文案字典、画布尺寸、输出目录与视觉常量从页面构图中分离。

### 合成细节

- **蒙版对比**：把两张相同尺寸、相同滚动位置的截图绘入同一个设备区域，再用斜向路径裁切第二张。分界线可用细白线和轻微紫光；不要把两个不同内容的列表伪装成同一状态切换。
- **浮层详情**：从实际详情截图裁出业务内容，保留足够边界；比例正确，增加小角度旋转与轻影，让浮层与首页形成空间关系。
- **双界面**：用前后关系或左右关系表达操作与结果。避免交叉盖住功能标题、水印或主要按钮。
- **解锁**：中间真实解锁页，两侧是真实内容的背景提示；使用透明度渐变蒙版衰减背景，避免硬裁切边缘，也不要模糊到变成无意义色块。
- **宽屏**：使用真实的并排布局截图，给它足够宽度。纵版营销页可以展示宽屏功能，宽屏上传栏位则另做横向构图。
- **设备边框**：原始截图已包含灵动岛等系统元素时，不再覆盖重复的岛或刘海；只有真实硬件素材才宣称是精确设备模型。轻量圆角和细边可作为中性界面框架。

各层的 clip、旋转、阴影和透明度要保存/恢复图形状态，避免前一层的蒙版裁掉后续标题。随机粒子使用固定种子，使多语言和后续重导出保持一致。

## 6. 多语言扩展

先定稿主语言的视觉和叙事，再扩展目标语言。为各页维护稳定 ID、主标题、重点行、副文案、标签和页脚；不要用文字位置或源字符串作为唯一长期标识。

英文重写为自然短句；繁体中文做词汇本地化，不只是字符转换，例如“文档/文件”“导出/匯出”“水印/浮水印”“本地/本機”。不要把某个地区用法强制应用于所有繁体市场。

每种语言重新测量文字宽高，调整断行与副文案长度。优先改写、换行和重排；避免为塞入同一框而把长英文无限缩小。导出前等待字体就绪，必要时用文字边界断言或布局检测发现溢出。

区别两种语言：

- **营销语言**：封面标题、副文案、标签。
- **界面语言**：真实 App 截图内部语言。

用户同意使用英文界面素材时，可以做其他语言营销封面，但应在交付中说明。需要完整本地化时，重新获取对应语言 UI 截图；不要把真实 UI 文案随意画掉后称为该语言的实际界面。

## 7. 尺寸、导出与本地验收

从 Apple 当前要求和实际 App Store Connect 栏位读取尺寸、方向与数量限制。不要仅凭设备营销名称推断像素，或把历史尺寸表当成永久规则。

已使用过的 1206 × 2622、1320 × 2868 纵图与 2853 × 2007 宽图仅是历史项目例子；1242 × 2688 曾作为设计母版。新项目须重新核实，母版和商店上传尺寸不是同一概念。

不同纵横比优先重排：文字重新定位、截图等比缩放、背景补足。轻微纵向尺寸差也应检查变形；横向版本必须单独构图，不能把整张纵图压扁。图库联系表、浏览页面截图和预览缩略图不作为最终商店素材上传。

导出建议为不带透明通道的 sRGB PNG。图片看起来不透明，不代表文件没有 alpha；在无 alpha 的目标画布上合成后输出。用图像工具确认实际色彩空间和可解码性，而不是仅根据扩展名或配置声称已验证。

每张做两次视觉检查：原尺寸看边缘、文字和裁切；商店缩略尺度看主标题、视觉层次和装饰是否仍成立。再看整组联系表，确认节奏统一、页面能区分。

结构检查脚本示例（仅使用 Python 3 标准库）：

```sh
python3 scripts/validate_exports.py /path/to/final/en-US/iphone-1206x2622 \
  --size 1206x2622 --count 6 \
  --manifest /path/to/final/en-US/iphone-1206x2622-manifest.json
```

脚本路径相对于 skill 根目录。它扫描指定目录直接包含的 PNG，不递归混入其他尺寸；检查 PNG 数据块完整性和 CRC、尺寸、透明通道、SHA-256。它不解压图像像素，也不验证 ICC 的内容，因此结构通过仍需图像解码、sRGB 和视觉检查。

## 8. 可选：App Store Connect 上传和处理验证

只在用户要求上传时执行。已有明确授权应延续，不能把“制作图片”自动扩大为提交审核。上传前确认当前可编辑版本、语言、设备栏位、替换范围和页序；多人同时发布时，尤其避免修改构建、版本文字或提交状态。

通过当前环境支持的浏览器或正式工具操作。复用已登录的目标页面；依据可见页面控件定位目标，不依赖私有后台接口、隐藏状态或会话提取。先读取现有内容，保留有用凭证，按语言和设备栏位逐组上传。

### 成功的证据

1. 数量与文件清单一致，顺序与设计一致。
2. 每张都显示真实缩略图；无持续云朵、Processing 或错误状态。
3. 有保存按钮且存在未保存变更时保存，等待完成。
4. 切换语言或刷新，再读回实际预览。网页工具支持只读检查时，可辅助确认图片 `complete` 且 `naturalWidth > 0`；同时保留可见页面凭证。
5. 最终记录每种语言每个设备栏位的结果，不以一组成功推断全部成功。

“6 of 10”只表示有 6 条资产记录，不能证明 6 张都完成处理。云朵可能短暂出现在上传/处理期间；如果刷新后仍持续出现，不能报告上传完成。页面没有提供原因时，不武断归因于网速或 Apple 后台。

### 持续占位的修复

先给处理留出合理时间，再刷新核对一次。若仍是占位，检查页面可见错误、上传规格和本地原图。不要快速重复上传或一遍遍清空全部语言。

已有替换授权且旧图可恢复时，只修复受影响的栏位：保留本地原文件与顺序；通过 UI 重试或重新关联/上传。如果使用 Remove All，先核实它只作用于目标组、旧素材仍可从资源库恢复，再执行。不要套用“删除一定可恢复”的假设。

重新上传后逐张核对实际图片、保存并刷新读回。一次有针对性的重传仍失败，就记录剩余失败项和页面错误，停止重复外部操作；若出现新的具体可修复原因，再据此处理。不要为追求“全部成功”误报或覆盖正常素材。

有一个实际案例：某语言中屏组显示 6 条记录，但前 4 张刷新后仍是云朵；重新上传该组后 6 张才全部正常。修复后还要核对其他语言与尺寸，最终以实际加载结果纠正先前仅按数量作出的结论。

## 9. 交付与可复现性

推荐把填好的简报、产品专属资料和结果保存在产品仓库：

```text
App Store Screenshots/
  brief.yaml
  source/                    可编辑源、文案、字体说明和运行方式
  raw/user-captures/          原始截图，名称描述实际内容
  final/<version>/
    index.html               可选的全部语言预览入口
    <locale>/
      master/                可选母版
      iphone-<width>x<height>/
      wide-<width>x<height>/
      contact-sheet.png
    image-manifest.json      文件、尺寸、方向、散列
    upload-status.json       如上传：逐语言/栏位记录
    proof/                   如上传：实际页面凭证
```

具体目录可适应已有项目。随交付说明生成命令、需要的运行时/字体、素材路径、语言、哪些图用于上传、哪些仅用于预览，以及未完成事项。不要把账号会话或开发者身份凭证打包进可共享资源。

上传状态区分“本地已导出”“已上传但处理中”“实际预览已验证并持久保存”“失败或待用户处理”。未执行的步骤写清楚，不用笼统的“已完成”覆盖全部阶段。只更新截图时，报告没有提交审核。

共享仓库维护通用说明、skill、模板与工具；产品专属文案、当前设备清单、源图和上传状态保留在消费项目。这让同一套方法能服务不同产品，而不会把旧项目的功能、账号或版本假设带到新项目。
